## 1. HIGH — 279 recovered posts are 404ing at their original URLs

This is new since the last audit and it is now the main event.

**The old permalink structure was `/%postname%/`.** Read directly from
`wp_options` in the Duplicator dump:

```
'permalink_structure','/%postname%/'
```

So every one of the old posts lived at a **root-level slug with a trailing
slash** — `https://kirstenrossiter.com/have-courage-to-stand-alone-if-you-must/`
— not under `/blog/`. The `?p=NNNN` values recorded as "Original URL" in
`WORDPRESS-POSTS-EXPORT.md` are the exporter's reconstruction from post IDs, not
the URLs Google indexed.

**Every one of them 404s today.** Sampled 8 across the full date range; all
behaved identically:

```
/have-courage-to-stand-alone-if-you-must/   apex=301  www=404
/the-power-of-his-joy/                      apex=301  www=404
/will-done-earth-heaven/                    apex=301  www=404
/we-are-the-change/                         apex=301  www=404
```

280 unique slugs, 279 published posts, 2016-08-27 → 2024-05-23. The Search
Console snapshot of 10 Jul recorded 18 404s — but that is only what Google still
held in its index at that moment, not the historical footprint. Eight years of
indexed content currently resolves to nothing.

`_redirects` says of these: *"Everything else from the old site is a real 404 now
that 404.html exists; redirecting dead posts to the blog index would be a soft
404 by another route."* That was the correct call in September, when the content
was gone. **It is no longer the right call, because as of 20 Oct the content
exists again.** The reasoning that justified the 404s has expired.

### Recommendation

Republish under `/blog/<slug>` and **301 from `/<slug>/`**. That keeps one
coherent content architecture (current posts already live at `/blog/<slug>`) and
recovers the equity on the old URLs via the redirect. Republishing at root slugs
would recover equity marginally more directly but splits the site into two blog
structures permanently — not worth it.

**Four things to handle, none of them optional:**

1. **Triage, do not bulk-publish.** 279 posts of 2016–2024 devotional writing
   will include genuinely short pieces. Publishing all of them unexamined trades
   one problem for a thin-content problem — Google does not reward 279 weak pages,
   and it would dilute the six strong current ones. Sort by length and substance,
   republish what stands up, and leave the trivial ones as 404s. A real 404 is a
   better outcome than a published 80-word page.
2. **One slug collision.** Old `keep-moving-forward` (2016-10-26) vs the current
   `/blog/keep-moving-forward` (2026). Different posts, same slug. The old one
   needs a distinct slug — date-qualify it.
3. **52 of 56 referenced media files are permanently lost.** Only 3 survive, in
   `blog/media/`, and they are currently orphaned (referenced by no published
   page). Any post republished with a reference to a missing file renders a broken
   image. Strip those references during the republish rather than after.
4. **`/blog/` will need pagination.** It is a flat list of 6 today. At 100+ it
   needs paging, and `buildHomepageInsights()`'s newest-3 logic should be checked
   against the much larger sorted set.

**Effort:** a day for the pipeline work, plus real editorial time on the triage.
**Impact:** high — this is the only item on this list that changes how much the
site can rank for at all.

### Status — 21 Oct 2026, later again: redirects generated, and the count is two, not nine

Done. `build-blog.js` gained `buildRedirects()`, which writes a marker block in
`_redirects` from the same published-post list `buildSitemap()` uses. A post
carrying a `legacy_path` cannot be published without its 301 appearing, and one
flipped back to draft loses it again. Both `/<slug>/` and `/<slug>` are emitted:
Cloudflare matches the source path as written and does not normalise the
trailing slash, which is why the hand-written rules list both forms too.
Everything above the markers stays hand-written, including the decision not to
redirect dead posts to the blog index — which still holds for every post that
stays a draft.

The old URL is data on the post, not inferred from its slug.
`import-archive-posts.js` now writes `legacy_path: /<slug>/` for every post
recovered from the **published** side of the export, and the 278 already-imported
files were stamped to match. Five guards in the build throw rather than emit a
bad rule: a malformed `legacy_path`, one under `/blog/`, one claimed by two
posts, one clashing with a hand-written rule, and missing markers.
`tests/redirects.spec.js` checks the generated block against `blog/posts/`
rather than a hand-kept list.

**Correction to the note above: only two of the nine live posts ever had an old
URL, not nine or even three.** This review listed `surviving-the-storm` with the

**The collision is resolved.** `/keep-moving-forward/` was the 2016 post, so
pointing it at the unrelated 2026 post of the same slug would be a wrong answer
rather than a recovery. The cause was subtler than "the draft needs a new slug":
the import *never created a file for the 2016 post at all*. It skips any slug
whose file already exists, `blog/posts/keep-moving-forward.md` was the 2026 post,
so the older one was silently dropped — which is also why it was not actually
among the 289 drafts, contrary to the note above. The import now detects that the
slug belongs to a different post (by date) and writes the file as
`keep-moving-forward-2016-10-26.md`, carrying `legacy_path: /keep-moving-forward/`.
Publish it and the old URL lands on the 2016 text; `/blog/keep-moving-forward`
stays the 2026 post. A test pins this.

**The Cloudflare cap is not a risk.** Pages allows 2,000 static redirects and 100
dynamic, 2,100 combined, with 1,000 characters per declaration. The whole archive
is 279 posts that had URLs × 2 forms = 558 rules, plus the 6 hand-written ones:
**564, about 28% of the static cap.** The longest rule is ~180 characters. No
truncation risk and no need for Bulk Redirects or a dynamic splat, so the
generated-static approach scales to the full republish as-is. The build throws if
the total ever crosses 2,000, and a test fails if the archive *would* cross it
once fully published, so the cap cannot be hit silently.

**What is left for the remaining 289 drafts:** nothing per-post. Flipping
`draft: false` and running the build is now sufficient — the redirect comes with
it. Two things to know:

- The **14 recovered WordPress drafts** carry no `legacy_path`, correctly, since
  they had no public URL. Thirteen of them are in `blog/posts/` under slugs
  derived from their titles.
- **One judgement call deferred.** `we-are-the-change` sits in the export's Drafts
  section but *does* have a slug, which WordPress only assigns on publish — so it
  was probably published once and later unpublished. This review sampled
  `/we-are-the-change/` as one of its 404s. It currently has no `legacy_path`,

  verified. If it is ever published here and Search Console shows the old URL had
  impressions, add `legacy_path: /we-are-the-change/` to it by hand; the build

## 2. MEDIUM — `blog/_template.html` is live and indexable

The one audit item (#7) that was never actioned, and the cheapest fix here.

```
https://www.kirstenrossiter.com/blog/_template.html   200
```

No `noindex`, no canonical. Its `<title>` is `Post title — Kirsten Rossiter`, its
meta description is `A short summary of this post.`, and its visible body carries
the build instructions ("Fill in the four EDIT markers below…"). Indexed, that is
an embarrassing result for a branded query.

`build-blog.js:91` acknowledges this in a comment and keeps the file in
`STATIC_HTML` anyway, so the build actively maintains a page it knows is
reachable.

**Fix:** add `<meta name="robots" content="noindex" />` to the template, and
`Disallow: /blog/_template.html` to `robots.txt`. **Effort:** 10 min.

**Status — 21 Oct 2026: done.** `noindex` added to `blog/_template.html`, and
`/blog/_template.html` added to the `NOINDEX` list in `tests/head.spec.js` so the
fix is guarded rather than just applied. The build preserves it (the marker
rewrite only touches the nav and footer blocks).

**The `robots.txt` disallow was deliberately _not_ added**, correcting the July
audit's advice to do both. `Disallow` and `noindex` work against each other: a
disallowed URL is not crawled, so Google never sees the `noindex` and an
already-indexed page can persist as a URL-only entry. `noindex` alone removes it
reliably. Once Search Console confirms the page has dropped out, a `Disallow` can
be added to save crawl budget — but not before.

Also noted while in the file: **the template's own instructions are stale.** It
tells you to copy the HTML file and hand-add a row to `blog/index.html`, but the
real workflow has been markdown in `blog/posts/` plus `npm run build` since the
pipeline landed. The file is arguably obsolete rather than merely unindexed.
Deciding whether to delete it is a separate call, since `build-blog.js`
references it in `STATIC_HTML` and in its orphan-cleanup skip.

## Not SEO, carried forward
### 8. The committed build output on `main` is stale

`becoming-the-place-of-his-rest` is published in markdown on `main`, but its
generated `blog/becoming-the-place-of-his-rest.html` is **not committed**, and it
is missing from the committed `blog/index.html` and `sitemap.xml`. Running
`npm run build` on a clean `main` produces all three as uncommitted changes.

**The live site is fine** — it serves the post at 200 and lists it in the live
sitemap — so Cloudflare is building on deploy. The drift is in the repository,
not in production. But it means the committed output is no longer a reliable
record of what is live, and anyone building locally gets a confusing diff that
is not theirs.

The `Build blog` workflow exists to prevent exactly this and did not catch it:
the bot's regenerate commit (`1019366`) landed without that post's HTML. The
workflow only triggers on pushes to `main` and skips its own `[skip ci]` commits,
so a CMS edit landing close to a bot run can be missed with nothing to show for
it.

**Fix:** trigger `Build blog` manually from the Actions tab (it has a
`workflow_dispatch` for precisely this case — "useful if a run is ever skipped").
One minute, no PR. Then work out how the run was missed, because it will recur.

**Status — 21 Oct 2026: fixed, and the cause was not what this section guessed.**
`Build blog` was dispatched on `main` and pushed `9f7f63a`, adding the missing
HTML and updating `blog/index.html` and `sitemap.xml`. `main` now serves 9 post
rows, lists the post in the sitemap, and `npm run build` on a clean checkout
produces no diff.

The run was **not skipped — it failed.** Run `39481825963` errored:

```
CONFLICT (content): Merge conflict in blog/index.html
CONFLICT (content): Merge conflict in sitemap.xml
error: could not apply 0523d7c... build: regenerate blog from markdown [skip ci]
```

Two edits landed close together. The first run built and pushed `1019366`; the
second built its own regenerate commit and then tried to **rebase** it onto a
`main` that already carried different generated output. `blog/index.html` and
`sitemap.xml` are wholly generated, so two generations of them conflict textually
every time. The rebase aborted and nothing was pushed.

**This will recur**, and the concurrency group does not prevent it — queuing the
runs is what creates the stale-base rebase. Generated files should never be
rebased: the job should pull or reset to the tip first and then **re-run the
build**, so the output is derived from the current source rather than merged with
someone else's copy of it. Worth fixing in `build-blog.yml` as its own change.

### 9. The visual regression baselines are stale and `main` is red

`blog-index` fails the screenshot diff on a **clean checkout of `origin/main`**
with no local changes — verified by stashing everything and running it on a
detached `origin/main`. The darwin baseline is 2084px tall; the page `main`
actually serves is 2442px. The baseline was captured when the blog had 6 posts
and was never regenerated after `surviving-the-storm` and
`the-dividing-of-the-army-ranks` were published.

So the failure predates and is independent of any current work, and the linux
baselines used by CI are almost certainly stale the same way — meaning
`visual-regression` will be red on any pull request until they are refreshed.

**Fix:** once item 8 is done and `main` is rebuilt, run `visual-regression` with
`update_baselines: true` on `main` to recapture. Do it in that order — rebaselining
before the output is correct would bake the stale page in, which is the exact
failure the workflow's own header warns about.

**Status — 21 Oct 2026: fixed, in that order.** `Build blog` first (finding 8),
then `visual-regression` with `update_baselines: true` on `main`, which pushed
`8105510`. It changed **exactly two files** — `linux/desktop/blog-index.png` and
`linux/mobile/blog-index.png` — and nothing else, which is the useful signal: no
other page had drifted, so the long-red check was not masking a second
regression.

**One correction to this section:** it assumed the darwin baselines were a repo
problem too. They are not — `tests/screenshots/darwin/` is **gitignored**
(`.gitignore:11`), so only the linux baselines are tracked and CI only ever uses
those. The stale darwin baseline was a purely local artifact on one machine,
fixed by `npm run test:visual:update` and committed nowhere.
